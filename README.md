# hizuke 0.2

画像を `YYYY-MM-DD HH.MM.SS.ext` にリネームする Rust CLI です。
EXIF を優先し、利用できなければファイル更新日時を使います。Dropbox 風の命名規則ですが、Dropbox の内部仕様を完全に再現するものではありません。

```text
IMG_1234.JPG → 2026-09-16 14.35.08.JPG
IMG_1235.JPG → 2026-09-16 14.35.08 (1).JPG
```

**普段は `hizuke 写真フォルダ` だけで使えます。** 端末では変更予定と重複の選択を確認して実行し、元の名前へ戻す履歴を自動で残します。設定ファイルは不要です。

## 気の利いたデフォルト

| 項目     | 何も指定しない場合                                                     |
| -------- | ---------------------------------------------------------------------- |
| 対象     | カレントディレクトリ。引数を渡せばそのディレクトリ                     |
| 実行     | 端末では予定を確認して実行。対話できない環境では読み取り専用プレビュー |
| 範囲     | 直下の画像。サブディレクトリは `--recursive` で明示                    |
| 日時     | EXIFのカメラ時刻、なければローカル時刻のmtime                          |
| 重複     | 残すファイルを質問。選ばれなかったコピーは復元可能な場所に退避         |
| 同名     | 自動で連番。既存ファイルは上書きしない                                 |
| 表示     | 変更点と要約を表示。すでに正しい名前の画像は件数で要約                 |
| 進捗・色 | 端末に合わせて自動調整。JSON・リダイレクト時は進捗なし                 |
| 読み取り | CPU数に合わせて最大4ファイルを並列処理。結果の順序は一定               |
| 中断     | Ctrl+Cで安全に停止。applyの途中なら元の名前への復帰を試みる            |

標準出力のリダイレクトやパイプを含め、標準入出力のどれかが端末でなければ既定は読み取り専用です。その場合に変更するには `--yes` を指定します。重複があるときは別途 `--duplicates keep-all` または `--duplicates skip` を明示します。明示的な `apply` はリダイレクト時も変更用コマンドとして扱い、端末での確認または `--yes` を求めます。

## インストール

Rust 1.89 以上でビルドできます。依存関係は `Cargo.lock` で固定しています。

```sh
cd /path/to/hizuke
cargo install --path . --locked
hizuke --help
```

同梱の `bin/hizuke` は、この実装環境でビルド・検証した macOS arm64 用バイナリです。インストールせず、プロジェクト内で `./bin/hizuke 写真フォルダ` と実行することもできます。
他の環境ではソースからビルドしてください。Linux / Windows 用の実装と CI 設定も含みますが、ローカルでの実機検証は macOS のみです。

### 旧名からの移行

プロジェクト名・コマンド名は `imgrename` から **`hizuke`** に変更しました。以後は `hizuke` を使用してください。シェル補完も `hizuke` 用に入れ替えます。

新しく作る履歴は `.hizuke` に保存します。旧版の `.imgrename` だけがあるディレクトリでは、その履歴を移動せず引き続き使用し、`history`・`undo`・`recover` も利用できます。既存の履歴を手動でリネームする必要はありません。両方の履歴ディレクトリが存在する場合は、履歴を使う操作をエラーにし、自動で統合しません。

## 基本操作

```sh
# 普段の使い方：現在のフォルダ、または指定フォルダを対話で処理
hizuke
hizuke ~/Pictures

# 変更予定を確認。画像・履歴ファイルを一切書き換えない
hizuke preview ~/Pictures
hizuke ~/Pictures --dry-run

# 重複の選択と最終確認をして実行
hizuke apply ~/Pictures

# サブディレクトリも対象にする。画像のあるディレクトリは変えない
hizuke apply ~/Pictures --recursive

# apply の読み取り専用モード
hizuke apply ~/Pictures --dry-run

# 構造化した変更予定
hizuke preview ~/Pictures --json

# 実行履歴、最新の完了処理を取り消す、中断処理を復旧する
hizuke history ~/Pictures
hizuke undo ~/Pictures --dry-run
hizuke undo ~/Pictures
hizuke recover ~/Pictures

# 特定の実行を指定する
hizuke undo ~/Pictures --transaction TRANSACTION_ID
hizuke history ~/Pictures --transaction TRANSACTION_ID

# シェル補完を出力する
hizuke completions zsh > _hizuke
```

ディレクトリ省略時はカレントディレクトリです。`plan` は `preview`、`rename` は `apply` の別名です。
`-r` は `--recursive`、`-y` は `--yes`、`-n` は `--dry-run` の別名です。`--dry-run` は `--yes` と併用しても常に変更しません。
`preview` と同名のディレクトリなら `hizuke ./preview` または `hizuke -- preview` と指定できます。

`--quiet` / `-q` は通常の表示を省き、質問とエラーだけを残します。`--verbose` / `-v` は変更しないファイルやファイルごとの警告も表示します。
色は `NO_COLOR` と端末判定に従い、`--color auto|always|never` で変更できます。これらと `--json` はサブコマンドの前後どちらでも指定できます。
`--dry-run` など処理固有のオプションは、明示したサブコマンドの後に指定してください。無視せず、位置が不正ならエラーにします。

## JSONと終了コード

`hizuke ./photos --json` は端末上でも読み取り専用です。変更する場合は `hizuke apply ./photos --json --yes` または `hizuke ./photos --json --yes` と明示します。
JSONではすべてのファイルと警告を省略せず出力します。変更予定には `schema_version: 1` と、日時の出所・変更数・総バイト数などの `summary` が含まれます。実行結果は取引IDと変更予定を一つのJSONとして返します。
実行時エラーも `--json` では一つのJSONです。引数の誤りはclapの使用方法エラーとしてstderrへ出力します。履歴一覧は従来互換のJSON配列です。

| 終了コード | 意味                                         |
| ---------- | -------------------------------------------- |
| `0`        | 成功、または変更不要                         |
| `1`        | 読み取り・競合・復旧などの処理エラー         |
| `2`        | コマンド引数が不正                           |
| `130`      | Ctrl+C、終了シグナル、対話での中止・確認拒否 |

## 日時の優先順位

1. EXIF `DateTimeOriginal` — 撮影日時
2. EXIF `DateTimeDigitized` — デジタル化日時
3. EXIF `DateTime` — 画像の作成・編集日時
4. ファイルシステムの更新日時（mtime）

不正な日付や空のタグは次の候補へ進みます。小数秒はファイル名に含めません。
更新日時を使った場合も、プレビューで `mtime` と明示します。

既定の `--timezone local` は EXIF に記録されたカメラの時刻をそのまま使用し、mtime は実行環境のローカル時刻で表します。
`--timezone utc` は EXIF の選択した日時タグに対応する `OffsetTimeOriginal` / `OffsetTimeDigitized` / `OffsetTime` が正しければ UTC に変換し、mtime も UTC で表します。
EXIF のオフセットが不明な場合、UTC と推測せず、警告付きでカメラの時刻を保持します。

## 完全一致する画像

対象の走査範囲全体で、ファイルサイズと SHA-256 による候補抽出の後、全バイト比較で完全一致を確認します。
ファイル名・更新日時が異なっていても内容が同じなら重複です。見た目が似ているだけの画像や、EXIF の内容だけ異なる画像は重複扱いしません。

`apply` の既定では、グループごとにファイル名・命名に使う日時・日時の出所を表示し、以下を選択できます。

- `1`、`2`、…：選んだファイルを画像ディレクトリに残す。残りは履歴内へ退避する。
- `a`：すべて残し、それぞれリネームする。
- `s`：そのグループはすべて変更しない。
- `q` または空入力：全処理を中止する。ここまで画像の変更はない。

退避先は `<対象ディレクトリ>/.hizuke/transactions/<ID>/duplicates/` です。旧版の履歴を引き継ぐ場合は `.imgrename` 内の同じ構造を使います。
退避ファイルは内部番号で保存され、元の名前との対応はジャーナルに記録されます。**ファイルは削除しません。** `undo` で退避分も元の場所に戻せます。
重複質問の後に最終的な変更予定を表示し、実行の確認を求めます。

対話できない環境では、重複があれば既定動作はエラーです。`--yes` は最終確認だけを省略し、残すファイルの選択を自動化しません。明示的に以下を指定できます。

```sh
# 全コピーを保持するバッチ処理
hizuke apply ./photos --duplicates keep-all --yes

# 重複グループを変更せず、重複のない画像だけ処理する
hizuke apply ./photos --duplicates skip --yes
```

`preview` / `--dry-run` は質問せず、既定では重複を `ASK` と表示します。この時点の変更数は、未選択グループを含みません。

## 名前の衝突と再実行

拡張子の大文字・小文字は維持します。同一秒の写真や既存ファイルと衝突したら、` (1)`、` (2)` の連番を拡張子の直前に追加します。
既存のファイル・ディレクトリ・リンクの名前を予約し、実行中に空く予定の名前も使い回しません。
大文字・小文字を区別しないボリュームでも衝突を避けるため、同じディレクトリ内では ASCII の大小文字を同一視して予約します。
日時に合った名前と正規の連番はそのまま保つため、同じオプションで繰り返しても番号が増え続けません。

## 安全性と復旧

- 画像の内容を書き換えず、ファイルの移動だけを行うため、EXIF と mtime を保ちます。
- OS の「既存の宛先を置き換えない」リネーム機能を使います。直前に別プロセスが宛先を作っても上書きしません。
- 処理前後にサイズ・SHA-256・mtime・Unix のファイル識別情報を検査します。スキャン中や確認待ちに変わった画像を検出すると停止します。
- 移動の意図を永続化してから画像を移動します。いったん全対象を履歴内に移し、それから最終名に移す二段階の処理です。
- 0.2以降の履歴は各記録のSHA-256と連続番号も別途同期します。途中の記録だけでなく、末尾の欠落・改変も検出して推測による復元を拒否します。0.1の履歴も読み取り・復元できます。
- 通常のエラーでは元の名前への復帰を試みます。復帰できなければファイルとジャーナルを保全し、復旧コマンドを案内します。
- 中断された処理があれば、新しい `apply` を拒否します。`recover` は元の名前に戻します。中断した `undo` も元の名前への復元を完了します。
- `undo` / `recover` は、画像が変更された、元の名前が別のファイルに使われている、といった場合に上書きせず停止します。競合を解消してから再実行できます。
- macOS / Linuxでは親子関係を含む重複した対象範囲への同時実行をディレクトリのOSロックで防ぎます。WindowsではOSの名前付きミューテックスで実行を直列化します。
- `history`、`history --transaction ID`、`undo --dry-run`、`recover --dry-run` は読み取り専用です。復元時には、変更前にファイルごとの元の名前を表示します。

Ctrl+Cを1回押すと、処理が安全に止まれる位置で中止します。apply中なら自動復元を試みます。undo / recover中の停止は履歴を残し、再度 `recover` で続けられます。2回目は即座に終了するため、次回は `recover` が必要になる場合があります。OSの読み取りが停止しているときなど、最初の中止要求が直ちに反映されない場合があります。

再帰走査中に別の `.hizuke` または旧版の `.imgrename` を持つサブディレクトリを見つけた場合、そのライブラリ全体を警告付きで除外します。各ライブラリはそれぞれのルートから処理してください。管理済みの親の配下で新しいライブラリを作ることも防ぎます。親が後から管理を始めた場合でも、すでに独立していた子ライブラリは引き続き使用できます。

`.hizuke`（旧版から引き継ぐ場合は `.imgrename`）は復旧に必要なデータです。途中で削除・編集・別の場所に移動しないでください。画像を含むディレクトリ全体を移動した場合も Unix のファイル識別情報が変わるコピー移動では `undo` が拒否されます。
0.2で更新した履歴は0.1で操作せず、0.2以降を使ってください。

原子的なリネームをファイルごとに行いますが、複数画像の変更全体が一瞬で切り替わるわけではありません。突然の終了では途中状態が残るため、次回 `recover` を使います。
電源断への耐性はファイルシステムと OS の同期保証に依存し、Windows ではディレクトリの `fsync` が利用できません。
画像編集アプリなど、hizuke以外のプロセスの書き込みはロックで完全には防げません。処理中は画像編集・同期による変更を止めてください。
特に Dropbox などの同期ディレクトリ、ネットワークドライブ、悪意あるプロセスがディレクトリを差し替える状況では、ローカルファイルシステムと同等の保証はできません。
再帰対象に別ファイルシステムのマウントが含まれる場合、ルートの履歴領域へのリネームができないためエラーになります。各ファイルシステムのディレクトリを個別に処理してください。

## 対応範囲

画像の検出は拡張子によります（大文字・小文字は不問）。画素のデコードによる画像検証はしません。

```text
jpg jpeg jpe tif tiff heic heif png webp avif gif bmp
dng cr2 cr3 crw nef nrw arw srf sr2 orf rw2 raf pef srw rwl
3fr fff iiq kdc dcr mos raw
```

EXIF の解析には [kamadak-exif](https://docs.rs/kamadak-exif/0.6.1/exif/) を使用し、JPEG / TIFF / HEIF / PNG / WebP などを扱います。
各 RAW 形式・AVIF などの EXIF 読み取り可否はコンテナに依存します。読めなければ mtime にフォールバックします。GIF / BMP も同様です。
大きな TIFF / TIFF 系 RAW は EXIF 解析を先頭 64 MiB に制限し、その外にあるタグは利用せず警告します。他のコンテナも EXIF 解析時の読み取り総量を1ファイル64 MiBに制限します。たとえば PNG の末尾にある EXIF までにこの制限を超えた場合は、警告付きで mtime を使います。ハッシュ計算と重複比較は全ファイルをストリーミングで読みます。最大4ワーカーで処理し、パーサー自体のメモリ使用量は読み取りバッファとは別に必要です。

シンボリックリンクを追跡せず、`.hizuke`・旧版の `.imgrename`・`.git` は再帰処理から除外します。それ以外の隠し画像は対象です。
走査・読み取りエラーでは、読み取れた分だけの部分実行をせず中断します。UTF-8 でないパスは明示的に拒否します。
対象は通常ファイルです。動画、サイドカーファイルの追随リネーム、類似画像判定、Dropbox API との連携は対象外です。

## 開発・検証

```sh
cargo fmt --check
cargo clippy --locked --all-targets -- -D warnings
cargo test --locked
cargo build --release --locked
```

単体・CLI 結合テストで、EXIF 優先順位、更新日時、重複、衝突、取り消し、実行中断、変更検出、リンク拒否などを確認します。
`.github/workflows/ci.yml` に macOS / Linux / Windows の検証ジョブを定義しています。
実際の検証結果と強制終了テストの再現手順は [TESTING.md](TESTING.md) に記載しています。

CLI は [clap](https://docs.rs/clap/latest/clap/) を使用しています。同時刻の大量画像の連番探索と履歴の検証は、ファイル数に対して二乗で増えないようにしています。全内容の読み取りと移動ごとの同期書き込みは維持しているため、巨大なライブラリでは時間がかかります。
