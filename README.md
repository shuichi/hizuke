# hizuke

<img src="icon.svg" width="140px" style="display: block; margin: 0 auto;">

hizuke は、画像や MP4 動画のファイル名を日時にそろえるコマンドラインツールです。
画像に記録された EXIF の日時や、MP4 内の作成日時を読み取り、`YYYY-MM-DD HH.MM.SS.ext` の形式に変更します。日時を取得できない場合は、ファイルの更新日時を使います。

```text
IMG_1234.JPG → 2026-09-16 14.35.08.JPG
IMG_1235.JPG → 2026-09-16 14.35.08 (1).JPG
VID_1236.MP4 → 2026-09-16 14.36.10.MP4
```

**基本の使い方は `hizuke 写真フォルダー` だけです。** 変更予定を確認し、重複ファイルの扱いを選んでから実行できます。元の名前に戻すための履歴は自動で保存されるので、設定ファイルを用意する必要はありません。

ファイル名は Dropbox に似た形式ですが、Dropbox の動作を完全に再現するものではありません。

## 標準の動作

| 項目 | 動作 |
| --- | --- |
| 対象フォルダー | 指定したフォルダー。省略した場合は現在のフォルダー |
| 処理範囲 | フォルダー直下の画像と MP4。サブフォルダーも含めるには `--recursive` を指定 |
| 実行前の確認 | 端末では変更予定を確認してから実行。対話できない環境では、標準でプレビューのみ |
| 日時 | 画像は EXIF、MP4 は動画内の作成日時を優先。取得できなければファイルの更新日時を使用 |
| 重複ファイル | 残すファイルを選択。残りは元に戻せるよう、履歴フォルダーへ退避 |
| 同じファイル名 | 連番を付けて区別。既存のファイルは上書きしない |
| 表示 | 変更点と集計結果を表示。すでに命名規則に合っているファイルは件数のみ表示 |
| 進捗と色 | 端末に合わせて調整。JSON 出力時やリダイレクト時は進捗を表示しない |
| 読み取り | CPU 数に応じて最大4ファイルを並列処理。結果の並び順は一定 |
| 中断 | Ctrl+C で停止。名前の変更中であれば、元の名前への復元を試みる |

サブコマンドを省略した場合、標準入力・標準出力・標準エラー出力のいずれかが端末でなければ、ファイルを変更せずプレビューだけを表示します。パイプやリダイレクトを使う場合も同じです。

対話できない環境で実際に変更するには `--yes` を指定してください。重複ファイルがある場合は、さらに `--duplicates keep-all` または `--duplicates skip` が必要です。`apply` を明示した場合は変更を実行するコマンドとして扱われ、端末での確認か `--yes` の指定を求めます。

## インストール

Rust 1.89 以上と、各 OS に対応するビルドツールが必要です。準備ができていれば、macOS・Windows・Linux のいずれでも次のコマンドでインストールできます。Windows では PowerShell またはコマンドプロンプトを使ってください。

```sh
cargo install --git https://github.com/shuichi/hizuke.git --locked
hizuke --help
```

GitHub からソースコードを取得し、お使いの OS と CPU に合わせてビルドします。あらかじめリポジトリをクローンする必要はありません。`--locked` を指定すると、リポジトリの `Cargo.lock` に記録されたバージョンの依存ライブラリを使います（[Cargo の公式ドキュメント](https://doc.rust-lang.org/cargo/commands/cargo-install.html)）。初回のインストールにはインターネット接続が必要です。

### Rust とビルドツールの準備

| OS | 必要な準備 |
| --- | --- |
| macOS | `xcode-select --install` を実行し、Command Line Tools をインストール |
| Windows | Visual Studio の「C++ によるデスクトップ開発」をインストール。MSVC と Windows SDK が必要（[公式手順](https://rust-lang.github.io/rustup/installation/windows-msvc.html)） |
| Linux | C コンパイラーとリンカーをインストール。Ubuntu / Debian では `sudo apt update` に続けて `sudo apt install build-essential curl ca-certificates` を実行 |

macOS / Linux で Rust をインストールするには、次のコマンドを実行し、画面の案内に従ってください。

```sh
curl --proto '=https' --tlsv1.2 -sSf https://sh.rustup.rs | sh
```

Windows では [Rust の公式インストールページ](https://www.rust-lang.org/tools/install) から CPU に合う `rustup-init.exe` をダウンロードして実行します。通常は標準の MSVC ツールチェーンを選びます。

インストール後に端末を開き直し、次のコマンドが実行できることを確認してください。Rust が 1.89 未満で、rustup を使って導入した環境であれば、`rustup update stable` で更新できます。

```sh
rustc --version
cargo --version
```

インストール後も `hizuke` が見つからない場合は、端末を開き直し、インストール先が `PATH` に含まれているか確認してください。標準の保存先は macOS / Linux では `~/.cargo/bin`、Windows では `%USERPROFILE%\.cargo\bin` です。`CARGO_HOME` やインストール先を変更している場合は、その配下の `bin` を確認します。

### 手元のソースコードからビルドする

このリポジトリの `Cargo.toml` があるフォルダーで、次を実行します。

```sh
cargo build --release --locked
```

実行ファイルは、Windows では `target/release/hizuke.exe`、macOS / Linux では `target/release/hizuke` に生成されます。

`hizuke` コマンドとしてインストールする場合は、次を実行してください。

```sh
cargo install --path . --locked
hizuke --help
```

## 基本の使い方

以下の `./photos` は、処理したいフォルダーのパスに置き換えてください。パスに空白が含まれる場合は、引用符で囲みます。

```sh
# 現在のフォルダー、または指定したフォルダーを処理する
hizuke
hizuke ./photos

# 変更予定だけを確認する。ファイルや履歴は書き換えない
hizuke preview ./photos
hizuke ./photos --dry-run

# 重複ファイルの扱いと変更予定を確認して実行する
hizuke apply ./photos

# サブフォルダーも処理する。各ファイルの保存先フォルダーは変えない
hizuke apply ./photos --recursive

# apply でも、--dry-run を付ければプレビューだけを表示する
hizuke apply ./photos --dry-run

# 変更予定を JSON で出力する
hizuke preview ./photos --json
```

フォルダーの指定を省略すると、現在のフォルダーが対象になります。`plan` は `preview`、`rename` は `apply` の別名です。

`--recursive` は `-r`、`--yes` は `-y`、`--dry-run` は `-n` と省略できます。`--dry-run` は `--yes` と同時に指定しても優先され、ファイルは変更されません。

フォルダー名が `preview` などのサブコマンド名と同じ場合は、`hizuke ./preview` または `hizuke -- preview` のように指定します。

### 履歴の確認と取り消し

```sh
# 実行履歴を確認する
hizuke history ./photos

# 直近に完了した処理の取り消し内容を確認し、元の名前に戻す
hizuke undo ./photos --dry-run
hizuke undo ./photos

# 中断した処理を復旧する
hizuke recover ./photos

# 実行 ID を指定して、取り消しや履歴の確認を行う
hizuke undo ./photos --transaction TRANSACTION_ID
hizuke history ./photos --transaction TRANSACTION_ID
```

### 表示とシェル補完

`--quiet`（`-q`）を指定すると、通常の出力を省き、質問とエラーだけを表示します。`--verbose`（`-v`）を指定すると、変更しないファイルやファイルごとの警告も表示します。

色の表示は端末の状態と `NO_COLOR` に従います。変更したい場合は `--color auto|always|never` を指定してください。これらの表示オプションと `--json` は、サブコマンドの前後どちらにも置けます。`--dry-run` など処理に関するオプションは、サブコマンドを使う場合はその後に指定します。位置が不正な場合はエラーになります。

Bash・Zsh・Fish 用の補完ファイルは [completions/](completions/) にあります。コマンドから生成することもできます。

```sh
hizuke completions zsh > _hizuke
```

## ファイル名に使う日時

### 画像

画像では、次の順に有効な日時を探します。

1. EXIF `DateTimeOriginal`：撮影日時
2. EXIF `DateTimeDigitized`：デジタル化された日時
3. EXIF `DateTime`：画像の作成・編集日時
4. ファイルの更新日時（mtime）

日付が不正な場合やタグが空の場合は、次の候補を使います。秒未満の値はファイル名に含めません。更新日時を使ったファイルは、プレビューに `mtime` と表示されます。

### MP4 動画

MP4 では、標準のムービーヘッダー `moov/mvhd` に記録された作成日時を使います。32ビット・64ビットの日時に対応しており、未設定（0）・欠落・不正な値の場合はファイルの更新日時を使います。

作成日時は1904年を起点とする UTC として読み取ります。編集や書き出しによって、実際の撮影日時とは異なる値になっている場合があります。メーカー独自の日時タグは読み取りません。

プレビューには、使った日時に応じて `MP4 creation_time` または `mtime` と表示されます。FFmpeg などの外部ツールは不要です。

### タイムゾーン

| 設定 | 画像の EXIF | MP4 の作成日時・ファイルの更新日時 |
| --- | --- | --- |
| `--timezone local`（標準） | カメラに記録された時刻をそのまま使用 | 実行環境のローカル時刻に変換 |
| `--timezone utc` | 対応する時差情報があれば UTC に変換 | UTC で表示 |

EXIF の時差情報には、採用した日時タグに対応する `OffsetTimeOriginal`・`OffsetTimeDigitized`・`OffsetTime` を使います。有効な時差情報がない場合は、`--timezone utc` を指定していてもカメラの時刻をそのまま使い、警告を表示します。

## 重複ファイルの扱い

処理対象の中から、内容が完全に一致するファイルを探します。まずファイルサイズと SHA-256 で候補を絞り、最後にファイル全体のバイト列を比較します。

名前や更新日時が違っていても、内容が同じなら重複と判断します。見た目が似ているだけの画像や、EXIF の内容が異なるファイルは重複として扱いません。

標準の設定で `apply` を実行すると、重複するファイルをグループごとにまとめ、名前・命名に使う日時・日時の出所を表示します。各グループの扱いは、次の選択肢から選べます。

| 入力 | 動作 |
| --- | --- |
| `1`、`2`、… | 選んだファイルを残し、残りを履歴フォルダーへ退避 |
| `a` | すべて残し、それぞれの名前を変更 |
| `s` | そのグループは変更しない |
| `q` または空入力 | 処理全体を中止。この時点ではファイルは変更されていない |

退避先は `<対象フォルダー>/.hizuke/transactions/<ID>/duplicates/` です。退避したファイルは内部番号で保存し、元の名前との対応を履歴に記録します。**ファイルは削除しません。** `undo` を使えば、退避したファイルも元の場所に戻せます。

重複ファイルの扱いを選んだ後、最終的な変更予定を表示して実行を確認します。

### 対話なしで実行する場合

`--yes` で省略できるのは最後の実行確認だけです。重複ファイルの扱いは自動で決まりません。対話できない環境で重複が見つかるとエラーになるため、次のどちらかを指定してください。

```sh
# 重複ファイルをすべて残し、それぞれの名前を変更する
hizuke apply ./photos --duplicates keep-all --yes

# 重複するグループはそのままにし、それ以外のファイルだけ処理する
hizuke apply ./photos --duplicates skip --yes
```

`preview` や `--dry-run` では質問を表示しません。重複の扱いが未選択の場合は `ASK` と表示し、そのグループを変更件数に含めません。

## 同じ名前になった場合と再実行

拡張子の大文字・小文字はそのまま残します。同じ秒のファイルが複数ある場合や、変更先の名前がすでに使われている場合は、拡張子の直前に ` (1)`、` (2)` のような連番を付けます。

名前の重複を調べる際は、既存のファイル・フォルダー・リンクをすべて確認します。処理中に空く予定の名前も使い回しません。大文字・小文字を区別しないファイルシステムでも安全に扱えるよう、同じフォルダー内では英字（ASCII）の大文字・小文字を同一視します。

日時に合った名前と正しい形式の連番がすでに付いているファイルは変更しません。同じ設定で繰り返し実行しても、連番が増え続けることはありません。

## 安全性と復旧

### ファイルと履歴の保護

- ファイル名の変更には移動操作を使い、画像・動画の内容やメタデータ、更新日時は書き換えません。
- OS の上書きを禁止するリネーム機能を使います。直前に別のプロセスが変更先のファイルを作った場合も、上書きしません。
- 処理前後にサイズ・SHA-256・更新日時を確認し、Unix ではファイルの識別情報も確認します。Windows でも読み取り後にファイルIDを照合し、日時やサイズが同じ別ファイルへの置き換えを検出します。読み取り中や確認待ちの間に変更を検出すると停止します。
- ファイルを移動する前に、予定する操作をディスクへ記録します。名前を変更するファイルはいったん履歴フォルダーへ移し、その後に最終的な名前で元のフォルダーへ戻します。
- 履歴の各記録には SHA-256 と連番も保存します。記録の欠落や改変を検出した場合は、推測で復元せず停止します。
- エラーが起きた場合は元の名前への復元を試みます。復元できない場合はファイルと履歴を残し、復旧コマンドを案内します。
- macOS / Linux では、親子関係を含めて処理範囲が重なる同時実行を OS のディレクトリロックで防ぎます。Windows では OS の名前付きミューテックスを使い、変更処理が同時に走らないようにします。

### 中断した処理を復旧する

Ctrl+C を1回押すと、安全に停止できる位置で処理を中断します。`apply` の途中であれば、自動的に元の名前への復元を試みます。`undo` や `recover` の途中で止めた場合は履歴を残すので、`recover` で復元を続けられます。

Ctrl+C を2回押すと即座に終了するため、次回の実行時に `recover` が必要になることがあります。OS の読み取り処理が止まっている場合などは、1回目の中断要求がすぐに反映されないことがあります。

未完了の処理が残っている間は、新しい `apply` を実行できません。`recover` を使い、元の名前に戻してください。復元前にファイルが変更されていたり、元の名前を別のファイルが使っていたりする場合は、上書きせず停止します。原因を解消してから再実行してください。

`history`、`history --transaction ID`、`undo --dry-run`、`recover --dry-run` は確認専用で、ファイルや履歴を変更しません。復元を実行する際も、先に元の名前をファイルごとに表示します。

### 履歴フォルダーの扱い

**`.hizuke` には復元に必要なデータが保存されています。削除・編集したり、別の場所へ移動したりしないでください。**

再帰的に処理している途中で、独自の `.hizuke` を持つサブフォルダーが見つかった場合は、その管理範囲全体を警告付きで除外します。それぞれのフォルダーを処理対象として指定してください。すでに管理されているフォルダーの配下で、新たに独立した管理を始めることも防ぎます。先に独立して管理されていたサブフォルダーは、親フォルダーの管理が始まった後も利用できます。

画像や動画を含むフォルダー全体を別の場所へコピーした場合、Unix のファイル識別情報が変わるため、`undo` で復元できないことがあります。

### 利用上の制約

ファイルごとのリネームは一度の操作で行いますが、複数ファイルの変更全体が同時に完了するわけではありません。突然終了すると途中の状態が残るため、次回は `recover` を使ってください。

電源断への耐性は、OS とファイルシステムの同期処理に依存します。Windows ではディレクトリの `fsync` を利用できません。また、hizuke のロックで他のアプリによる書き込みを完全に防ぐことはできないため、処理中は編集アプリや同期アプリによるファイルの変更を止めてください。

Dropbox などの同期フォルダー、ネットワークドライブ、別のプロセスによってフォルダーが差し替えられる環境では、ローカルのファイルシステムと同じ保護は保証できません。

サブフォルダーに別のファイルシステムがマウントされている場合は、履歴フォルダーへリネームで移動できずエラーになります。ファイルシステムごとに対象フォルダーを分けて実行してください。

## 対応形式と読み取りの制限

ファイルは拡張子で判別し、大文字・小文字は区別しません。画像や動画をデコードして、正常に表示・再生できるかを検証する機能はありません。

```text
jpg jpeg jpe tif tiff heic heif png webp avif gif bmp
dng cr2 cr3 crw nef nrw arw srf sr2 orf rw2 raf pef srw rwl
3fr fff iiq kdc dcr mos raw
mp4
```

EXIF の読み取りには [kamadak-exif](https://docs.rs/kamadak-exif/0.6.1/exif/) を使い、JPEG・TIFF・HEIF・PNG・WebP などに対応しています。RAW 形式や AVIF では、ファイルの構造によって EXIF を読み取れない場合があります。その場合や GIF・BMP などで日時を取得できない場合は、ファイルの更新日時を使います。

大きな TIFF や TIFF 系 RAW では、EXIF の解析範囲を先頭 64 MiB に制限します。それより後にあるタグは使わず、警告を表示します。他の画像形式でも、EXIF 解析時の読み取り量は1ファイルにつき合計 64 MiB までです。必要な日時を取得する前に上限へ達した場合は、警告を表示し、更新日時を使います。

MP4 の日時を調べる際は、動画本体を読み飛ばし、ヘッダーを探します。探索は最大100,000ボックスまでに制限し、上限への到達や破損を検出した場合は、警告を表示して更新日時を使います。

ハッシュの計算と重複確認では、形式にかかわらずファイル全体を少しずつ読み取ります。一度に処理するのは最大4ファイルで、メタデータの解析には読み取り用バッファとは別にメモリを使います。ファイル全体の確認や移動ごとの履歴の同期が必要なため、大きなファイルや大量のファイルを扱う場合は時間がかかります。

処理対象は通常のファイルだけです。シンボリックリンクはたどらず、`.hizuke` と `.git` は読み取り対象から除外します。それ以外の隠しファイルも、対応する拡張子であれば対象になります。フォルダーの読み取りやファイルの読み取りに失敗した場合は、その時点で中断し、読み取れた分だけを変更することはありません。UTF-8 で表せないパスもエラーになります。

MP4 以外の動画、関連するサイドカーファイルの一括リネーム、見た目が似た画像の判定、Dropbox API との連携には対応していません。

## JSON 出力と終了コード

`hizuke ./photos --json` は、端末で実行してもプレビューのみです。変更を実行する場合は、次のように `--yes` を付けてください。重複がある場合は、重複の扱いも指定します。

```sh
hizuke apply ./photos --json --yes --duplicates keep-all
```

JSON には、すべてのファイルと警告を省略せず出力します。変更予定には `schema_version: 1` と、件数・日時の出所・合計サイズなどをまとめた `summary` が含まれます。`summary.exif_dates`、`summary.mp4_dates`、`summary.mtime_dates` は、それぞれの日時を使ったファイル数です。変更を実行した場合は、実行 ID と変更予定をひとつの JSON として返します。

`--json` を指定した場合、実行時のエラーもひとつの JSON として出力します。ただし、コマンドの引数が不正な場合は、使い方を示すエラーメッセージを標準エラー出力に表示します。履歴一覧の JSON 出力は配列です。

| 終了コード | 意味 |
| --- | --- |
| `0` | 正常終了、または変更の必要なし |
| `1` | 読み取り・名前の競合・復旧などでエラーが発生 |
| `2` | コマンドの引数が不正 |
| `130` | Ctrl+C や終了シグナルによる中断、対話中の中止、実行確認での拒否 |

## 開発と検証

```sh
cargo fmt --check
cargo clippy --locked --all-targets -- -D warnings
cargo test --locked
cargo build --release --locked
```

開発時のルールは [AGENTS.md](AGENTS.md) に記載しています。ビルドと Clippy は、警告も含めてゼロにする方針です。

単体テストと CLI の結合テストでは、EXIF と MP4 の日時、更新日時への切り替え、重複、同名ファイル、取り消し、中断からの復旧、変更の検出、リンクの拒否などを確認します。CI の設定は [.github/workflows/ci.yml](.github/workflows/ci.yml) にあり、macOS・Linux・Windows でテストとインストールを検証します。

CLI の引数解析には [clap](https://docs.rs/clap/latest/clap/) を使用しています。
